# GitHub Copilot Harness

GitHub Copilot harness 适配器通过 Agent Client Protocol (ACP) 将 `HarnessAgent` 连接到 [GitHub Copilot CLI](https://github.com/github/copilot-cli)。该适配器将 ACP 安装、会话、流式传输、工具、审批和生命周期管理委托给 `@ai-sdk/harness-acp`。

<Note>
  Harness 包目前处于**实验阶段**。随着这一早期 API 的进一步完善，各版本之间可能会出现破坏性变更。
</Note>

## 设置

<InstallPackages packages="@ai-sdk/harness @ai-sdk/harness-github-copilot @ai-sdk/sandbox-vercel" />

ACP harness 会在首个会话启动时，在沙箱内安装固定版本的 GitHub Copilot CLI。它绝不会使用宿主机或全局安装的 Copilot CLI。启动命令会禁用 GitHub Copilot 的自动更新，以便安装的版本在该引导过程中保持固定。

## 导入

```ts
import {
  createGitHubCopilot,
  githubCopilot,
} from '@ai-sdk/harness-github-copilot';
```

`githubCopilot` 等同于使用默认配置的 `createGitHubCopilot()`。

## 基本用法

```ts
import { HarnessAgent } from '@ai-sdk/harness/agent';
import { githubCopilot } from '@ai-sdk/harness-github-copilot';
import { createVercelSandbox } from '@ai-sdk/sandbox-vercel';

const agent = new HarnessAgent({
  harness: githubCopilot,
  model: 'gpt-5.5',
  sandbox: createVercelSandbox({
    runtime: 'node24',
    ports: [4000],
  }),
});

const session = await agent.createSession();

let exitCode = 0;
try {
  const result = await agent.stream({
    session,
    prompt: 'Check the test failures and fix the production code.',
  });

  for await (const part of result.stream) {
    if (part.type === 'text-delta') {
      process.stdout.write(part.text);
    }
  }
} catch (err) {
  exitCode = 1;
  console.error(err);
} finally {
  await session.destroy();
  process.exit(exitCode);
}
```

要将此智能体与 Vercel Sandbox 配合使用，请在宿主环境中提供 `VERCEL_OIDC_TOKEN` 以及[身份验证](#authentication)下列出的变量之一。

会话支持多轮对话、附加与分离、冷停止与恢复、轮次暂停与继续，以及通过共享 ACP 桥接生命周期进行 `stopWhen` 切片。

## 适配器设置

使用 `createGitHubCopilot()` 配置运行时：

```ts
const harness = createGitHubCopilot({
  auth: 'ai-gateway',
  reasoningEffort: 'high',
  port: 4001,
  startupTimeoutMs: 180_000,
});
```

设置项：

- `auth`：选择 `auto`、`direct` 或 `ai-gateway` 身份验证，或接受一个隔离的身份验证环境。默认值为 `auto`，当存在 Gateway 凭据时选择 AI Gateway，否则选择直接 GitHub Copilot 身份验证。
- `credentialForwarding`：可选的同步或异步回调，用于在 harness 适配器将每个凭据转发到沙箱进程之前立即对其进行自定义。它接收原本会被转发的凭据值（真实凭据或掩码值）以及用于暴露该凭据的环境变量名。此回调仅控制转发到沙箱进程中的值。它不会限制 harness 适配器在宿主进程中能够发现、读取或以其他方式访问哪些凭据。
- `reasoningEffort`：支持推理的模型的推理强度。支持的值为 `none`、`minimal`、`low`、`medium`、`high`、`xhigh` 和 `max`。省略时，GitHub Copilot 使用其配置的默认值。
- `mcpServers`：以服务器名称为键的 ACP 原生 stdio、HTTP 或 SSE MCP 服务器定义。
- `port`：ACP 桥接端口覆盖。
- `portEndpoint`：当沙箱会话无法直接暴露端口时，ACP 桥接的宿主端点。
- `startupTimeoutMs`：等待 ACP 桥接启动的最长时间。
- `reconnect`：已建立的桥接 WebSocket 连接断开后的重连时机。`maxElapsedMs` 控制总重试窗口，包括连接建立和退避延迟，默认值为 30 秒。`initialDelayMs` 默认值为 50 毫秒，`maxDelayMs` 默认值为 2 秒。这些重试使用指数退避，并且与 `startupTimeoutMs` 相互独立。当沙箱、桥接进程或桥接端点永久不可用时，它们无法恢复。
- `mintBridgeToken`：同步函数，接收沙箱 id 并返回 ACP 桥接身份验证令牌。默认情况下，适配器会生成一个随机的 32 字节令牌。自定义实现必须返回一个足够保密的令牌。

`reasoningEffort` 对启动的 GitHub Copilot 服务器是固定的，并适用于它创建的每个会话。

适配器固定了 GitHub Copilot CLI、可执行文件、启动命令和 ACP 版本。这些实现细节无法通过 `createGitHubCopilot()` 覆盖。

## 身份验证

GitHub Copilot 支持直接 GitHub 身份验证和 AI Gateway 身份验证。设置以下一个或多个环境变量：

- `COPILOT_GITHUB_TOKEN`
- `GH_TOKEN`
- `GITHUB_TOKEN`
- `VERCEL_OIDC_TOKEN`
- `AI_GATEWAY_API_KEY`
- `AI_GATEWAY_BASE_URL`

如果未设置任何适用的凭据环境变量，除非选择了 AI Gateway 身份验证，否则适配器会尝试从宿主系统解析原生订阅。

对于直接身份验证，GitHub Copilot 按所列顺序检查三个 GitHub 令牌变量。细粒度个人访问令牌需要 **Copilot Requests** 权限；不支持经典个人访问令牌。对于 AI Gateway，适配器使用 `VERCEL_OIDC_TOKEN` 或 `AI_GATEWAY_API_KEY`，并遵循 `AI_GATEWAY_BASE_URL`。

当沙箱支持请求转换时，适配器仅将每个凭据代理到匹配的出站请求。其他沙箱在应用 `credentialForwarding` 后保留直接凭据转发。

当宿主在运行时解析凭据时，传入一个身份验证环境：

```ts
const gatewayHarness = createGitHubCopilot({
  auth: {
    AI_GATEWAY_API_KEY: await resolveGatewayToken(),
    AI_GATEWAY_BASE_URL: 'https://ai-gateway.vercel.sh',
  },
});
```

提供的记录会替换用于身份验证发现的宿主环境。适配器不会将其凭据添加到 `process.env`，也不会将其值包含在持久化的 ACP 生命周期标识中。

当两种凭据都可用时，强制使用特定的身份验证路由：

```ts
const directHarness = createGitHubCopilot({ auth: 'direct' });
const gatewayHarness = createGitHubCopilot({ auth: 'ai-gateway' });
```

AI Gateway 模型请求不需要 GitHub 身份验证，但内置的 GitHub MCP 功能需要。

## 沙箱

GitHub Copilot 通过 `@ai-sdk/harness-acp` 在沙箱内运行。它需要一个至少暴露一个端口的网络沙箱：

```ts
const sandbox = createVercelSandbox({
  runtime: 'node24',
  ports: [4000],
});
```

首个会话需要网络出口来安装 GitHub Copilot CLI。后续的模型、GitHub、Web 和 MCP 请求也需要网络访问。

## 内置工具

适配器将 `bash`、`grep` 和 `glob` 映射到相应的通用 harness 工具。

其他工具仍以其原生 GitHub Copilot 名称可用，包括 `read_bash`、`stop_bash`、`list_bash`、`view`、`create`、`edit`、`web_fetch`、`skill`、`sql`、智能体工具和 `task`。GitHub 和用户配置的 MCP 工具保持动态。

当 GitHub Copilot 发送权限请求时，共享 ACP harness 会应用配置的 Harness `permissionMode`。`allow-reads` 批准读取操作，`allow-edits` 还会批准文件修改，`allow-all` 批准所有请求。在 `allow-edits` 下，Shell 执行仍需要审批。

## 已知限制

- ACP v1 并未为每个原生工具事件暴露稳定的编程名称。适配器使用标准的 title、kind 和 schema 匹配，并将未匹配的工具保持为动态。
- ACP v1 不暴露模型步骤边界或每步用量。当 GitHub Copilot 未提供总计值时，适配器会推断边界并报告未知的每步用量。
- ACP v1 没有可移植的手动压缩或轮次中途引导 API。
- ACP v1 没有可移植的内置工具过滤 API。支持过滤宿主工具，但过滤 GitHub Copilot 内置工具会抛出不支持能力的错误。
- GitHub Copilot 目前不支持内置工具审批请求。请在此适配器中使用 `permissionMode: 'allow-all'`。宿主执行的 AI SDK 工具审批仍然有效。
- GitHub Copilot ACP 不暴露结构化输出元数据映射，因此不支持基于 schema 的结构化输出。
- GitHub Copilot ACP 不暴露任何提问工具，因此不支持 `askUserQuestions`。
- GitHub Copilot CLI 不会通过 ACP 为任何模型呈现推理内容。`reasoningEffort` 控制推理深度，而非可见性：发出推理摘要需要一个参数，而 ACP 的 `session/new` 和 `session/set_config_option`（仅限于 `mode`、`model`、`reasoning_effort`、`allow_all` 和 `agent`）从不向客户端暴露该参数。唯一设置它的代码路径位于 GitHub Copilot 的交互式终端 UI 中，而该 UI 不会在无头 `--acp --stdio` 模式下运行。
- 原生不支持自定义 `headers`，仅通过沙箱外部请求转换应用。因此，当提供不具备该能力的沙箱时，无法传递自定义 `headers`，它们会被忽略。
