# 中止与可恢复流

## 问题

当使用 `useChat` 并设置 `resume: true` 进行流恢复时，客户端的中止操作会被视为断开连接。关闭标签页、刷新页面、导航离开或调用 `stop()` 都会关闭当前的 HTTP 连接，但这不应取消正在进行的生成过程。

如果您的应用将请求中止信号传递给模型调用，断开连接可能会取消流恢复期望继续运行的工作。如果您的停止按钮仅调用 `stop()`，服务端的生成过程可以继续，客户端可以重新连接到同一个活跃流。

```tsx
const { messages, stop } = useChat({
  id: chatId,
  resume: true, // 启用流恢复
});

// stop() 仅中止当前客户端请求。
// 它不是服务端取消请求。
```

## 背景

流恢复允许客户端在原始连接关闭后重新连接到活跃流。为了支持这一点，即使没有客户端连接，服务端也需要保持流生产者运行。

这意味着路由清理、页面卸载和网络断开应作为可恢复的断开连接处理。明确的用户取消需要一个单独的服务端信号，用于取消活跃的生产者并清除存储的活跃流引用。

## 解决方案

使用 `resume: true` 在断开连接后重新连接，并为明确的用户取消添加专用的停止端点。

停止端点应：

1. 加载聊天记录并读取其活跃流 ID
2. 如果客户端发送了最新的部分助手消息，则持久化该消息
3. 取消正在生成流的工作
4. 仅当活跃流引用仍指向同一流时，才清除该引用

在客户端，在停止本地聊天流之前调用您的停止端点：

```tsx
const chat = useChat({
  id: chatId,
  resume: true,
});

async function stopStream() {
  await fetch(`/api/chat/${chatId}/stop`, { method: 'POST' });
  chat.stop();
}
```

将导航与停止行为分开。不要在路由清理代码、页面卸载处理程序或组件卸载清理中调用停止端点。这些事件属于断开连接，应保持可恢复性。

如果您不需要流恢复，仅需客户端取消，请禁用 `resume` 并直接使用 `stop()`：

```tsx
const { messages, sendMessage, stop } = useChat({
  id: chatId,
  resume: false, // 禁用流恢复（默认行为）
});
```
