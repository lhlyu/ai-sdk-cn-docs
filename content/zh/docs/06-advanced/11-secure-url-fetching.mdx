# 安全的 URL 获取

许多提供商会在**响应体中返回一个 URL**——一个待下载的生成图像、音频或视频，或一个用于检查任务状态的轮询 URL。AI SDK 会在服务端获取这些 URL，并将结果返回给你的代码。由于该 URL 来自外部服务，恶意或已被攻陷的提供商（或任何能够篡改响应的人）可能将其指向内部地址，例如云元数据端点（`http://169.254.169.254/…`）、私有主机（`http://10.0.0.5/…`）或 `localhost`。

为防止这种情况，SDK 会在获取之前验证每个由响应提供的 URL。这一过程在提供商包内部自动完成——你无需进行任何配置。

对于需要认证的任务状态轮询，提供商可以基于配置的 API 端点构造第一个 URL。SDK 信任该配置的源用于初始请求，但会手动跟随并验证每一次离开该源的跳转。MiniMax、Kling AI 和 ByteDance 的视频轮询使用此受保护路径。

## SDK 防护的内容

当 SDK 获取来自提供商响应的 URL 时，它会：

- **拒绝私有、回环和链路本地目标**——IPv4（`10/8`、`172.16/12`、`192.168/16`、`127/8`、`169.254/16`、CGNAT、多播等）及等效的 IPv6 范围，以及 `localhost`、`.local`、`.localhost` 和 `.internal` 主机名。非 `http(s)` 协议也会被拒绝。
- **重新验证每一次重定向跳转**——一个通过验证但随后重定向到内部地址的 URL 会被阻止；重定向绝不会被盲目跟随。
- **在 Node.js 上于连接时验证 DNS**——每个解析出的地址都会被检查，并且套接字会固定到已验证的 DNS 结果，因此 DNS 重绑定无法在验证与连接之间引入不同的地址。
- **剥离有风险的请求头**——代理转发、云元数据和 cookie 头会在请求前被移除。
- **跨源时丢弃凭据**——调用方请求头（`Authorization`、`Cookie` 以及提供商特定的 API 密钥头）不会被发送到与提供商不同源的主机；跨源的重定向会丢弃除 user-agent 之外的所有这些头。

被阻止的 URL 会以 `DownloadError` 的形式暴露。

## 直接获取不受信任的 URL

对于使用 `@ai-sdk/provider-utils` 的自定义集成，当 URL 来自响应或其他不受信任的输入时，请使用 `fetchUntrustedUrl`。它会验证 URL 和重定向，并在首次请求时扣留凭据和未知的自定义头，除非该 URL 与配置的源匹配：

```ts
import { fetchUntrustedUrl } from '@ai-sdk/provider-utils';

const response = await fetchUntrustedUrl({
  url: result.downloadUrl,
  headers: {
    authorization: `Bearer ${apiKey}`,
    accept: 'image/*',
  },
  credentialedOrigin: providerBaseURL,
});
```

此处，仅当初始 URL 与 `providerBaseURL` 具有相同的源时，才会发送 `Authorization`。否则，只会发送允许列表中的元数据，例如 `Accept`、`Range` 和 `User-Agent`。跨源重定向会丢弃除 `User-Agent` 之外的所有调用方请求头，并且凭据绝不会在后续跳转中重新附加。

`credentialedOrigin` 必须来自你的配置，绝不能来自响应 URL。它不会禁用 URL 验证。对于配置的私有端点，还需传入 `trustedOrigin`；如果省略 `credentialedOrigin`，`fetchUntrustedUrl` 会使用 `trustedOrigin` 作为允许接收凭据的源。可以通过 `untrustedFirstHopHeaders: ['x-protocol-version']` 允许额外的协议元数据。只列出可以安全地向任何目标披露的请求头；凭据请使用配置的源。

现有的 `fetchWithValidatedRedirects` 辅助函数保留其首次请求行为：它会清理有风险的请求头，但仍会转发认证和自定义头。切换到 `fetchUntrustedUrl` 以启用首次请求的凭据隔离。现有的 `getFromApi` 调用也保留其行为；在使用凭据获取由响应提供的 URL 时，请传入 `credentialedOrigin`。

## 自托管和本地端点

与**你配置的**提供商端点同源的 URL（例如指向自托管或 `localhost` 部署的自定义 `baseURL`）不受这些检查的限制——它们的目标正是你告诉 SDK 要通信的主机。这也适用于任务状态轮询。任何离开该源的重定向在发送重定向请求之前仍会被验证。

## 跨运行时的 DNS 验证

在 Node.js 上，默认的已验证下载获取使用 `node:dns` 和 `undici` 连接器钩子在连接时验证每个解析出的地址。连接器使用这些确切的结果，从而同时关闭主机名到私有 IP 和 DNS 重绑定的绕过途径。

包装或替换全局 `fetch` 不会禁用此保护：默认的 Node.js 下载传输独立于全局 `fetch`。

Bun、Deno、Cloudflare Workers 和框架边缘运行时使用其平台 fetch，即使它们暴露了 Node 兼容的 `process` 对象。

如果你显式注入自定义 `fetch`，则它负责等效的 DNS 验证和连接固定。其他运行时不暴露 Node 的 DNS/套接字钩子，因此在这些运行时上的服务端部署应限制网络出口到私有、回环、链路本地和云元数据范围。

## 加固你的部署

如果你的服务器获取由提供商提供的 URL，并且你想关闭 DNS 缺口，请使用以下一种（理想情况下两种）方法：

### 1. 在网络层限制出站出口

拒绝你的服务器网络出口到 `169.254.0.0/16`、RFC-1918 范围和回环。这是最稳健的控制措施，且独立于应用代码。

### 2. 加固注入的 `fetch`

Node.js 默认已经固定。如果你显式注入自定义 `fetch`，请使用 `undici` 的 `Agent` 作为其后端，其 `connect.lookup` 验证解析出的 IP，并仅允许套接字连接到安全地址——从而同时关闭主机名到私有地址和 DNS 重绑定的窗口：

```ts
import { Agent, fetch as undiciFetch } from 'undici';
import { lookup } from 'node:dns';

// Your own check that returns true for private/loopback/link-local addresses.
declare function isUnsafeAddress(ip: string): boolean;

const safeLookup: typeof lookup = (hostname, options, callback) => {
  lookup(hostname, options as any, (err, address, family) => {
    if (!err && typeof address === 'string' && isUnsafeAddress(address)) {
      callback(new Error(`Refusing to connect to ${address}`), '', 0);
      return;
    }
    (callback as any)(err, address, family);
  });
};

const safeDispatcher = new Agent({ connect: { lookup: safeLookup } });

const safeFetch: typeof fetch = (input, init) =>
  undiciFetch(input, { ...init, dispatcher: safeDispatcher }) as any;
```

```ts
import { createFal } from '@ai-sdk/fal';

const fal = createFal({ fetch: safeFetch });
```

SDK 的 URL 验证和你自定义 fetch 的连接时固定是互补的——请同时保留两者。
