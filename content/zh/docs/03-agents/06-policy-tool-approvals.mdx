# 基于策略的工具审批

[工具审批](/docs/agents/tool-approvals) 允许你在智能体设置中使用函数来批准或拒绝工具调用。`@ai-sdk/policy-opa` 将这些规则从代码中移出，放入用 `.rego` 编写的 [Open Policy Agent](https://www.openpolicyagent.org/) (OPA) 策略中。

当你希望授权具备以下特性时使用它：

- 作为独立的、可审查的工件编写，而不是隐藏在智能体设置中的函数。
- 在 CI 中可使用 `opa test` 进行测试，独立于 SDK。
- 无需代码部署即可编辑（当从运行的 OPA 实例提供服务时）。

该包完全构建在公共 `toolApproval` 回调之上。在通信层面没有任何变化：与内置审批相同的 `tool-approval-request` / `tool-approval-response` 流程。

## 你可以强制执行什么

OPA 是一个通用的策略引擎。如果你能将规则表达为对结构化输入的代码，你就可以在工具边界强制执行它。常见类别：

- **安全与访问**：范围、角色、权限、租户隔离、工具、主机或路径的允许列表。
- **业务规则**：谁可以在哪些资源上做什么，在什么条件下（例如，超过阈值的付款需要审批）。
- **成本与用量**：拒绝或要求审批超出预算、令牌上限或每用户配额的调用。
- **合规与变更控制**：在正确的审批人、环境或时间窗口内，对破坏性或受监管的操作进行把关。

决策不仅限于当前调用的参数。策略 `input` 还携带 `messages`，即运行时的完整模型和工具调用历史，因此规则可以考虑已经发生的事情：先前的工具调用、到目前为止的操作序列，或整个对话中的累计总数。示例：

- 一旦运行已经执行了 N 次写入操作，则要求审批。
- 在同一个对话中拒绝第二次不可逆操作（推送、删除）。
- 跨步骤跟踪累计支出或令牌使用情况，并在达到上限时停止。

### 最佳适用场景：确定性检查

当决策是确定性的并且可以从结构化字段（无论这些字段来自当前调用还是 `messages` 中的历史记录）进行验证时，策略强制执行最为有效。策略提取一个值并进行比较，因此每次答案都是相同的。

- **强适用场景**：范围、权限、数字阈值、允许列表、时间窗口以及基于历史记录的检查，如计数、序列和累计总数。
- **弱适用场景**：基于内容或语义的过滤，例如“不要使用不良语言”或“阻止有毒内容”。这些是尽力而为的，难以验证，且容易绕过。为此使用专门的审核或分类步骤，并将策略用于围绕它的确定性关卡。

经验法则：如果你可以指向 `input` 对象中的一个字段并对其编写精确检查，那么这是正确的工具。如果规则依赖于判断自由形式的含义，则不要仅仅依赖策略。

## 安装

```sh
pnpm add @ai-sdk/policy-opa
# 选择一个（或两个）OPA 后端：
pnpm add @open-policy-agent/opa-wasm   # 进程内 WASM 评估
pnpm add @open-policy-agent/opa        # 连接到运行中 OPA 服务器的 HTTP 客户端
```

- 后端是可选的 peer 依赖项。
- 仅加载你导入的后端。

## 工作原理

在每次工具分发之前都会咨询策略，并映射到标准审批状态之一：

- `allow` 运行工具。
- `deny` 返回一个模型可以推理的拒绝结果（无需人工）。
- `requires-approval` 暂停运行并等待人工 `tool-approval-response`。
- 没有匹配的规则会规范化为 `not-applicable`，SDK 将其视为允许。在你的策略中添加 `default decision := { "decision": "deny" }` 以默认拒绝。

## 快速开始

```ts
import { generateText } from 'ai';
import { anthropic } from '@ai-sdk/anthropic';
import { opaPolicy, wasmPolicyClient } from '@ai-sdk/policy-opa';
import { readFile } from 'node:fs/promises';

// 1. 加载编译后的策略包。
const wasm = await readFile('./policy.wasm');
const client = await wasmPolicyClient({ wasm });

// 2. 构建 toolApproval 配置。
const toolApproval = opaPolicy({
  client,
  path: 'agent/call/decision',
});

// 3. 将其传递给 generateText（或 streamText / ToolLoopAgent）。其他一切正常。
const result = await generateText({
  model: anthropic('claude-sonnet-4-5'),
  tools: { git, bash, queryLogs },
  toolApproval,
  prompt: '找到失败的测试并推送修复',
});
```

## 编写 Rego 策略

策略发出一个决策对象。`reason` 是可选的，会返回给模型（对于 `deny`）或人工审批者（对于 `requires-approval`）。

```rego
package agent.call

# 默认为 "not-applicable"，以便未匹配的调用通过。
# 使用 { decision: "deny" } 来默认拒绝。
default decision := { "decision": "not-applicable" }

# 硬拒绝：推送永远不允许自动进行。
decision := { "decision": "deny", "reason": "推送需要人工审核" } {
  input.tool.name == "git"
  input.args.args[0] == "push"
}

# 自动允许：只读的 git 操作。
decision := { "decision": "allow" } {
  input.tool.name == "git"
  input.args.args[0] in {"status", "log", "diff", "show"}
}

# 人工介入：由值班人员执行的 kubectl。
decision := { "decision": "requires-approval", "reason": "由值班人员执行的 kubectl" } {
  input.tool.name == "kubectl"
  input.runtimeContext.role == "sre-oncall"
}
```

注意：

- 也接受旧的布尔形状（`{ "allow": true | false, "reason": "..." }`），因此现有规则无需重写即可迁移。
- 默认的 OPA `input` 形状是 `{ tool: { name }, args, messages, runtimeContext }`。
- 使用 `toInput` 覆盖输入形状：

```ts
opaPolicy({
  client,
  path: 'agent/call/decision',
  toInput: ({ toolCall, runtimeContext }) => ({
    action: toolCall.toolName,
    principal: runtimeContext.role,
    resource: toolCall.input,
  }),
});
```

### 在 CI 中测试策略

OPA 自带其测试框架。这些测试无需 SDK 即可运行，这是策略即代码优于策略即应用代码的主要原因。

```rego
# policy_test.rego
package agent.call

test_push_denied {
  decision.decision == "deny" with input as {
    "tool": { "name": "git" },
    "args": { "args": ["push", "origin", "main"] }
  }
}
```

使用 `opa test policy.rego policy_test.rego` 运行。

### 错误时默认拒绝

- 如果后端出错（服务器不可达、WASM 故障、构建错误的包），`opaPolicy` 返回 `denied`，并将错误消息作为原因。
- 错误永远不会从回调中拒绝，也永远不会中止运行。
- 后端中断会阻止受影响的调用，而不是静默允许它。
- 这与返回不匹配的规则不同，后者会规范化为 `not-applicable`（允许）。如果你也希望未匹配的调用被拒绝，请使用 `default ... deny` 规则。

## 加载策略

### 选项 A：WASM（进程内）

提前将 `.rego` 编译为 WASM：

```sh
opa build -t wasm -e 'agent/call/decision' -o bundle.tar.gz policy.rego
tar -xzf bundle.tar.gz /policy.wasm
```

```ts
import { wasmPolicyClient, opaPolicy } from '@ai-sdk/policy-opa';
import { readFile } from 'node:fs/promises';

const wasm = await readFile('./policy.wasm');
const client = await wasmPolicyClient({ wasm });
const toolApproval = opaPolicy({ client, path: 'agent/call/decision' });
```

- 每次决策无需网络调用。
- 适合将策略与应用一起发布，或在启动时从对象存储中获取。
- 热重载意味着重建 WASM 并重新实例化客户端。

### 选项 B：HTTP（运行中的 OPA 服务器）

```ts
import { httpPolicyClient, opaPolicy } from '@ai-sdk/policy-opa';

const client = httpPolicyClient({ url: 'http://localhost:8181' });
const toolApproval = opaPolicy({ client, path: 'agent/call/decision' });
```

- 每次决策一次 HTTP 往返。
- 适合策略频繁更改且希望无需重新部署即可热重载，或多个服务共享一个 OPA 的情况。
- 传递 `headers` 用于 Styra DAS / EOPA 认证。

## 引入外部数据和集成

策略不限于工具调用的输入。OPA 可以基于外部数据做出决策，例如角色到权限的映射、IDP 组成员身份、权利列表或允许列表，并且这些数据可以在不重新部署应用的情况下更新。

OPA 如何获取数据是 OPA 的事情，不是这个包关心的。常见方法：

- **加载时的静态数据**：将 `data` 传递给 `wasmPolicyClient({ wasm, data })`。它被传递给包的 `setData`，因此策略可以在 `data.*` 下读取它。
- **包**：将运行中的 OPA 服务器（HTTP 后端）指向一个包服务，以便它定期拉取新的策略和数据。角色映射和 IDP 组更新无需代码部署。
- **评估期间的查找**：策略可以在评估决策时调用外部服务（例如 IDP 或权利 API）。

从 OPA 了解详细信息，而不是这里：

- [策略参考](https://www.openpolicyagent.org/docs/policy-reference)
- [外部数据](https://www.openpolicyagent.org/docs/external-data)（包括连接到 IDP）

此包仅将结果决策映射到 SDK 的审批状态。它传递的 `input` 是你的策略与 OPA 已有的任何数据相结合的内容。

## 使用影子模式安全推出

不要直接将新策略投入强制执行。第一个版本几乎总是会拒绝你本意不想拒绝的东西。`shadow(approval, opts)` 评估策略并通过 `onDecision` 报告决策，但告诉 SDK 每个调用都获得批准，直到你翻转 `enforce: true`。

```ts
import { opaPolicy, shadow, wasmPolicyClient } from '@ai-sdk/policy-opa';

const client = await wasmPolicyClient({ wasm });

const toolApproval = shadow(
  opaPolicy({ client, path: 'agent/call/decision' }),
  {
    enforce: process.env.ENFORCE_POLICY === 'true',
    onDecision: event => {
      logger.info('policy.decision', {
        tool: event.toolCall.toolName,
        decision: event.decision.type,
        reason: event.decision.reason,
        enforced: event.enforced,
        wouldBlock: event.decision.type === 'denied',
      });
    },
  },
);
```

推荐的推出步骤：

1. 编写策略并使用 `opa test` 进行测试。
2. 将其包装在 `shadow(...)` 中，设置 `enforce: false`（默认值），并将 `onDecision` 连接到你的日志/指标。
3. 在你的真实环境中运行。检查 `decision.type` 为 `denied` 或 `user-approval` 的事件：这些是策略会改变的调用。
4. 修复策略并迭代。
5. 当唯一的 `denied` / `user-approval` 事件是你想要的事件时，设置 `enforce: true`。

遥测语义：

- `onDecision` 是即发即弃的。缓慢或抛出异常的记录器不能阻塞或破坏强制执行，并且抛出的错误会被吞掉。
- 约定是强制执行优先，可观测性其次。
- 对于相反的情况（强制执行等待审计日志），从底层 `toolApproval` 内部记录，而不是通过 `shadow`。

## 将决策发送到你的可观测性平台

`onDecision` 不仅用于推出。保持 `shadow` 就位并设置 `enforce: true`，每个决策都会流向你的日志记录、指标或跟踪堆栈，同时策略保持承载。

```ts
const toolApproval = shadow(
  opaPolicy({ client, path: 'agent/call/decision' }),
  {
    enforce: true, // 强制执行并观察
    onDecision: event => {
      metrics.increment('agent.policy.decision', {
        tool: event.toolCall.toolName,
        decision: event.decision.type, // approved | denied | user-approval | not-applicable
        enforced: String(event.enforced),
      });
    },
  },
);
```

- 每个 `PolicyDecisionEvent` 携带工具调用、策略 `decision`（类型和原因）、`enforced` 和 `effective`（SDK 实际执行的内容）。比较 `decision` 与 `effective` 以发现偏差。
- `onDecision` 是即发即弃的；请参阅影子模式下的遥测语义。

当你使用 HTTP 后端时，OPA 还可以原生发出[决策日志](https://www.openpolicyagent.org/docs/management-decision-logs)，将每次评估发送到远程服务以获取完整的审计跟踪，而无需任何应用代码。

## 在模型边界进行能力范围界定

`opaCapabilityMiddleware` 比 `toolApproval` 更早地强制执行策略：在模型被告知存在某个工具之前。这是纵深防御，此外它还可以节省令牌并提高越狱拒绝能力。

```ts
import { wrapLanguageModel } from 'ai';
import { wasmPolicyClient, opaCapabilityMiddleware } from '@ai-sdk/policy-opa';

const client = await wasmPolicyClient({ wasm });

const wrappedModel = wrapLanguageModel({
  model: anthropic('claude-sonnet-4-5'),
  middleware: opaCapabilityMiddleware({ client, path: 'agent/tools/allowed' }),
});
```

- `path` 处的规则返回一个允许的工具名称的 `string[]`，或 `{ tools: string[] }`。
- 不在允许列表中的工具在模型看到它们之前被丢弃。
- 失败时关闭：在格式错误的响应或评估器错误时，`params.tools` 被设置为 `undefined`，因此模型被告知它没有工具。要失败时打开，请在 Rego 中编写回退。

## 界定已发现工具的范围

当工具来自 MCP 发现或插件注册表时，你无法提前编写每个工具的规则，并且你忘记的任何工具都会被静默允许。`wrapMcpTools` 通过将未匹配的工具路由到可配置的默认值，使审批覆盖已发现的表面。

```ts
import { opaPolicy, wasmPolicyClient, wrapMcpTools } from '@ai-sdk/policy-opa';

const discovered = await mcpClient.tools();
const client = await wasmPolicyClient({ wasm });

const { tools, toolApproval } = wrapMcpTools(
  discovered,
  opaPolicy({ client, path: 'agent/call/decision' }),
  { default: 'user-approval' }, // OPA 未匹配的任何内容都需要人工
);

await generateText({ model, tools, toolApproval, prompt });
```

未覆盖工具的默认值：

- `'user-approval'`（默认）：需要人工。适合当你信任来源但想要安全网时。
- `'denied'`：硬允许列表模式。策略枚举允许的内容；其他所有内容都被拒绝。
- `'approved'`：允许。仅当发现源完全受信任时。

尽管名称如此，但它适用于任何 `Record<string, Tool>`。

## 未配置策略时全部允许

`optionalOpaPolicy` 在 `client` 为 `undefined` 时返回 `undefined`，这与不传递 `toolApproval` 相同（SDK 批准每个调用）。适用于本地开发或策略文件不存在的 CI。

```ts
import { optionalOpaPolicy, wasmPolicyClient } from '@ai-sdk/policy-opa';
import { readFile } from 'node:fs/promises';

const wasm = process.env.POLICY_WASM_PATH
  ? await readFile(process.env.POLICY_WASM_PATH)
  : undefined;

const client = wasm ? await wasmPolicyClient({ wasm }) : undefined;

const toolApproval = optionalOpaPolicy({ client, path: 'agent/call/decision' });
```

- `POLICY_WASM_PATH` 未设置：`toolApproval` 为 `undefined`，所有调用都允许，OPA 模块从不加载。
- `POLICY_WASM_PATH` 已设置：策略加载，强制执行开启。
- 对于更严格的行为（拒绝在没有策略的情况下启动），直接使用 `opaPolicy` 并让缺失的字节在启动时抛出。

## 传递性强制执行：复合工具

`toolApproval` 仅在模型直接调用工具时触发。一个粗粒度的调度器工具（一个可以运行 `git push` 的 `bash` 工具、一个 HTTP 工具、一个 MCP 代理）允许模型通过路由来绕过每个操作的规则。

修复方法位于调度器的 `toolApproval` 条目内部：将调度器输入解析为逻辑上的 `(name, args)` 对，然后针对与直接工具相同的规则进行评估。

```ts
const bashApproval = opaPolicy({
  client,
  path: 'agent/action/decision',
  toInput: ({ toolCall }) => {
    const { command } = toolCall.input as { command: string };
    const [bin, ...rest] = command.split(/\s+/);
    return { kind: bin, args: rest };
  },
});
```

指导：

- 将匹配逻辑保持在一个地方：要么是共享的 Rego 辅助规则（两个审批都使用相同的 `path` 调用 `opaPolicy`），要么是共享的 TypeScript 谓词。
- 拒绝任何你无法简化为干净调用的内容。Shell 输入是对抗性的，难以解析，因此“无法证明它是安全的”意味着拒绝。
- 诚实的限制：这在模型的调用边界处对分发进行把关。它不会阻止一个工具在被批准后执行超出其输入描述的额外副作用。为此，在带外沙箱（Vercel Sandbox、Firecracker、容器）中运行不受信任的执行，并将沙箱视为信任边界。

SQL、HTTP、MCP、浏览器和 Shell 调度器的工作示例位于[包 README](https://github.com/vercel/ai/tree/main/packages/policy-opa) 中。

## 示例应用

[ai-sdk-slackbot](https://github.com/vercel-labs/ai-sdk-slackbot) 示例将此包端到端地连接到一个真实的智能体中。它展示了：

- 每个工具调用都由 `policies/decision.rego` 中的 Rego 把关，无需接触 TypeScript 即可编辑。
- 策略下的真实工具：一个限定域名的网络搜索、一个带有城市允许列表的天气工具，以及一个限制为只读命令允许列表的 `bash` 工具（传递性强制执行）。
- 使用一个环境变量（`POLICY_MODE`）切换后端：默认是进程内 WASM，或者用于在开发中热重载策略的实时 OPA HTTP 服务器。
- 策略代码使用 `policies/decision_test.rego` 中的 OPA 原生测试独立测试。

有关如何加载和应用策略，请参阅 [`policies/`](https://github.com/vercel-labs/ai-sdk-slackbot/tree/main/policies) 和 [`lib/policy/load.ts`](https://github.com/vercel-labs/ai-sdk-slackbot/blob/main/lib/policy/load.ts)。

## API 参考

所有内容都从包根目录 `@ai-sdk/policy-opa` 导出。

引擎中立核心：

- `shadow(approval, opts?)`：包装任何审批，使其被评估和报告，但在 `opts.enforce: true` 之前不强制执行。推荐用于任何新策略的起点。
- `wrapMcpTools(tools, approval, opts?)`：使审批覆盖已发现的工具集。`opts.default` 控制未覆盖的工具。
- `PolicyClient`：每个后端实现的 `evaluate(path, input)` 接口。非 OPA 引擎的接缝。
- 辅助类型：`PolicyDecision`、`WrappedMcpTools`、`PolicyDecisionEvent`。

OPA 后端和适配器：

- `wasmPolicyClient({ wasm, data? })`：异步；在进程中加载编译后的 OPA WASM 包。
- `httpPolicyClient({ url, headers? })`：同步；针对运行中 OPA 服务器的客户端。
- `opaPolicy({ client, path, toInput? })`：返回一个 `toolApproval` 配置。失败时关闭。
- `optionalOpaPolicy({ client, path, toInput? })`：类似于 `opaPolicy`，但在 `client` 为 `undefined` 时返回 `undefined`。
- `opaCapabilityMiddleware({ client, path, toInput? })`：一个 `LanguageModelV4Middleware`，它将 `params.tools` 缩小到允许列表。失败时关闭。
- `normalizeOpaDecision(result)`：独立的结果规范化，适用于自己调用 OPA 的用户。
